# 自分たちのベンチマーク（設計）

目的は「最初はこうだったが、こうやったらこの辺が良くなった」を、素材と結果で確かめられるようにすること。数字の平均だけでは、どこが良くなり、どこが悪くなったかが見えない。だから、場面ごとに分けた素材と、変更の前後を並べて見られる結果をセットで持つ。

## 1. 素材（固定して、版で管理する）

場面ごとのタグを付けた、正解マスク付きの画像と短い動画。

| タグ | 何を見るか |
| --- | --- |
| `hands` | 手指。顔の前の手、手を振る、指を立てる、物を持つ |
| `hair` | 髪の毛先、くせ毛、まとめ髪 |
| `edge` | 肩・首・服の輪郭 |
| `motion` | 動き。連続フレームでのちらつき、速い動きでの遅れ |
| `light` | 逆光、暗い部屋、顔だけが明るい |
| `similar-bg` | 背景が服や肌と似た色 |
| `accessory` | 眼鏡、ヘッドホン、マイク |
| `partial` | 体の一部だけが写る、画面の端で切れる、複数人 |

ルール:
- 素材は版を付けて固定する（`v1`, `v2` …）。追加や修正をしたら版を上げ、何を変えたかを記録する。版が違う結果どうしは比べない
- 学習に使ったデータは素材に入れない。素材は学習に使わない
- 入力は実務の条件にそろえる。640×480、24fps 相当の動画
- 出典とライセンスを1件ずつ記録する。公開できない素材は「非公開」と印を付け、手元の評価だけに使う

素材の集め方の候補:
- EasyPortrait のテスト分割（ビデオ会議に近い）から、タグごとに選ぶ
- Open Images の手のマスク（`hands` の補強）
- 動画は、正解マスク付きで使えるライセンスのものが少ない。足りなければ、人物の切り抜き素材を背景に合成して作る。最後の手段として、人間に短い動画を撮ってもらう（相談事項）

### 正解マスクがない実写素材の扱い

素材は2種類に分ける。

- **数値用**。正解マスクのある公開データ（EasyPortrait のテスト分割など）。メイン指標と下層指標はこちらで計算する
- **見た目用**。正解マスクのない実写。数字は出さず、前後の合成結果と誤差の出やすい場所を並べて、目で見て改善を確かめる。「徐々に良くなっていく」ことを確かめるための素材

見た目用だけで「改善した」とは言わない（AGENTS.md の「数字で言えない改善は改善として扱わない」）。補助として、重くて精度の高いオフラインのモデルで「仮の正解」を作り、それとの一致度を参考値として出すことはできる。ただし、仮の正解は本物の正解ではない。参考値にとどめ、メイン指標には使わない。

## 2. 結果（実行ごとに残す）

1回の評価を「ラン」と呼ぶ。ランごとに `bench/results/<ラン ID>/` を作り、次のものを残す。

- `meta.json`: モデル、コミット、素材の版、日時、計測した環境、そのランで試した仮説
- `metrics.json`: 素材1件ごとの数字と、タグごとの集計
  - 精度: IoU、Boundary F
  - 動き: 隣り合うフレームのマスクの差分（ちらつき）
  - 速さ: 1フレームの処理時間（前処理・推論・後処理の内訳、p50 と p95）。基準環境の Chrome で WebGPU と WASM の両方を測る
- 見た目の証拠: 素材ごとの画像を3枚
  - 合成結果
  - マスクを重ねた画像
  - 誤差マップ（余分に残した部分を赤、削りすぎた部分を青）

## 3. 比べるページ

2つのランを選ぶと、1枚の HTML で比べられるようにする。

- タグごとの表: 前、後、差分。良くなったタグと悪くなったタグがひと目で分かるように
- 素材ごとの並び: 前後の誤差マップを左右に並べ、改善が大きい順と悪化が大きい順に見られるように
- 速さの表: 処理時間の前後

これが「最初はこう、こうやったらここが良くなった」の証拠になる。

今あるのは `bench/compare.py`。`eval_person_iou.py` の結果 JSON とモデル名の組を1つのランとして、指標の表と、person IoU の改善・悪化が大きい画像の誤差マップを出す。タグごとの表はまだない。誤差マップは推論し直して描くので、結果 JSON と数字が合わない画像には印を付ける。

`--fingers BEFORE.jsonl:MODEL AFTER.jsonl:MODEL` を付けると、`finger_core.py` の出力から指の生存率の表も足す（#3）。指は（画像、手、指）の組で対応を取り、指の種類ごとの生存率と、全画素で集計した指の芯の再現率を並べる。対応を取った差の標準誤差は、`finger_summary.py` と同じく画像を単位にする。「kept now / lost now」は、前は消えていて後で残った指と、その逆の数。

`--latency BEFORE.json AFTER.json` を付けると、`bench/browser/latency.html` の結果から、それぞれのランのモデルの1フレームの時間（p50 / p95）を、モードと入力ごとに並べる（#3）。1回のブラウザ計測で両方のモデルを測ったときは、同じファイルを2回渡す。`GPU_TEXTURE` の行には、合格条件（p95 で 8 ms 以下、#28）の判定を前後で出す。

## 4. 履歴

`bench/results/index.json` に全ランを並べ、メイン指標の推移をグラフで見られるようにする。各ランは、Hillclimb の判断記録（仮説、結果、採用したかどうか）とつなげる。

## 5. 最初に測るもの

改善の出発点として、手を入れる前に次の2つを測る。

- `selfie_multiclass_256x256`（PC の基準）
- `selfie_segmenter_landscape`（モバイルの基準）

## 6. 公開について

ベンチマークそのもの（素材の一覧、ハーネス、比べるページ）は、それだけで公開する価値がある可能性がある。ブラウザでの人物切り抜きを、精度と速さで同じ条件のもとに比べた表は、まだ見つかっていない。公開すれば、サブ指標（スター数や利用者）につながる可能性がある。公開する前に、人間に確認する。
